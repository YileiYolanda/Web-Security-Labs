# Information disclosure in error messages

## Description
This lab's verbose error messages reveal that it is using a **vulnerable version of a third-party framework**. To solve the lab, obtain and submit the version number of this framework.

## Solution
1. Choose a product and forward the GET request
2. Find `/product?productid=2` in HTTP history and send to Repeater
![Send to Burp Repeater](lab01-01.png)
3. Modify the productid to a non-integer, such as 'productid=yolanda'
4. At the end of the Response we can find the version number of this framework, which is `Apache Struts 2 2.3.31`
![Send to Burp Repeater](lab01-02.png)

## Question
1. WHY attacker want to know the framework version?
help an attacker identify the technology used by the website and search for known vulnerabilities affecting it.

2. WHY we send the wrong format will lead to leakage of framework version?
- **Exception:** server tries to convert `yolanda` into an integer,
  but the conversion fails and an exception occurs
- **Information disclosure:** error handling mechanism return detailed diagnostic information to the user

3. Is the information leak caused by the vulnerable framework version?
It does not tell us whether the error page was generated by application code or by the framework's error handling.
Exposing detailed errors and using a vulnerable framework version are separate problems. Both need to be addressed.

## Concluion
1. The application should validate input on the server side.
2. Invalid input should receive a simple, appropriate error response.Detailed stack traces should be kept in logs with restricted access.
3. Vulnerable components should be patched or upgraded promptly.
4. Hiding version numbers reduces information exposure, but it does not fix vulnerabilities in the framework itself.
